---
name: multica-project-resource-contract
description: "Use before working with a supplied benchmark or fixed resource/submission contract. Not needed for routine coding, research or issue coordination."
---

Read the supplied project.json and guide before choosing the documented solution location and exact dev command. Preserve the benchmark, evaluator, partitions, metric and private evaluation boundary. Reuse supplied environments and data within the stated CPU and resource limits. Do not create a replacement evaluator, validation protocol, setup tree or publication layer.

Follow the project's sharing and evidence locations. A shared GitHub resource does not authorize publishing Multica evidence there. The direct parent owns common instructions and integration; each child owns its solution changes. Keep datasets, credentials and private answers outside the repository.

In a benchmark-solving task, an infrastructure failure is an external prerequisite: preserve its exact command and error and request parent help through `multica-surface-block`. That assignment does not authorize changing platform source, services, deployment, runtime configuration or fixed evaluation resources. An explicitly assigned infrastructure fix follows its own scope.

The configured submission kind and path are the delivery contract. A file submission remains that canonical file; a runnable script or directory does not replace it. Measure the supplied starter artifact first; delegate improvements instead of rebuilding the baseline in the parent. When a worker generates separate dev and final outputs, commit the final output at the configured submission path. The parent checks that exact path at the reviewed commit before merging and again after integration.
