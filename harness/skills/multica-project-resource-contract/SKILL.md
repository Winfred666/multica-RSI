Read the supplied project resources and repository guide in the current checkout. Use the documented solution location and exact benchmark.py dev command; preserve the benchmark, partitions, metric and private evaluation boundary. Reuse supplied environments and data. Respect CPU and resource limits. Do not create a new evaluator, validation protocol, setup tree or publication layer.

Issue metadata identifies the Git repository URL, branch and parent branch. Native project resources locate the checkout; Git locates its worktree. Use the current issue's selected sub-issue exec and returned workdir for repository work; the native task directory is bootstrap context. The seed checkout can remain on main. Run the selected SOP's exec -- pwd to locate the current issue's worktree before treating its branch as missing. Reuse the bound repository instead of checking out another copy from the GitHub resource. Share accepted facts, code and evidence through the supplied shared GitHub resource and project folder. The direct parent owns common project instructions and integration; each child owns its solution changes and research/<issue>/ evidence. Keep datasets, credentials and private answers outside the repository.

An infrastructure problem is an external_prerequisite: preserve its exact command and error and report it to the parent. Never change platform source, services, deployment, runtime configuration or fixed evaluation resources.
The configured submission kind and path are the delivery contract. A file submission remains that canonical file; a runnable script or directory does not replace it. Read the repository project.json/guide before choosing the dev command. Measure the supplied starter artifact first; delegate improvements instead of rebuilding the baseline in the parent. When a worker generates separate dev and final outputs, commit the final output at the configured submission path. The parent checks that exact path at the reviewed commit before merging and again after integration.
